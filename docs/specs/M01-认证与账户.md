# M01 认证与账户

> 依赖：M00。被依赖：所有模块（`ctx.user`）。

## 1. 目标与功能对齐
旧版功能（全部保留）：
- 统一登录入口：先输入邮箱（"继续"），不暴露账号是否存在。
- 邮箱验证码：发送、校验；已有账号直接登录，新账号补填昵称和密码完成注册。
- 密码登录。
- Google 登录；已登录账号绑定 Google。
- 忘记密码：邮箱验证码 → 设置新密码 → 自动登录。
- 登出；修改密码后旧会话失效。
- 登录、发码限流（数据库持久化）。
- 邮件通过 Resend 发送，按用途使用不同模板。
- 邮箱大小写不敏感。
- 会话过期时弹出重新登录，登录后回到原页面。
- 自部署单用户模式（M15 约定）：`SEMESTRA_SINGLE_USER=true` 时，首次访问创建管理员账户（邮箱 + 密码），之后关闭注册；该模式下也允许 `EMAIL_BACKEND=console`（验证码打印到日志）。同源托管（`SEMESTRA_SERVE_WEB`）时 Cookie 不设 `COOKIE_DOMAIN`，且 `PUBLIC_API_ORIGIN` 可能是 `http://`（自部署内网/本机），`Secure` 应取决于该 origin 的协议；后端的 GET 路径不得与前端路由同名。

新增（为 iOS 与 MCP 预留，同属本模块）：
- Token 认证：access token + refresh token（原生客户端使用）。
- 会话管理：查看并撤销登录设备。
- 个人访问令牌（PAT）：供 MCP 客户端使用，带作用域。
- 账户资料：昵称、头像（可选，使用 Google 头像或首字母）、修改邮箱（需新邮箱验证码）、修改/设置密码、解绑 Google（至少保留一种登录方式）。

账户删除和数据导出见 M13。

## 2. 数据模型
```

  id, email (unique, 存小写), email_verified_at, display_name, avatar_url?,

  id, user_id, provider ('google'), subject (unique with provider), email, created_at

  last_used_at, expires_at, revoked_at?
auth_email_challenges
  id, email, purpose ('continue'|'reset_password'|'change_email'), code_hash, attempts,
  max_attempts (5), expires_at (10 分钟), last_sent_at, verified_at?, consumed_at?,
  verification_token_hash?, request_ip, user_agent, provider_message_id?
auth_rate_limits
  id, scope, key_hash, attempts, window_started_at, blocked_until?

```
注：表名遵循 M00 前缀规则，`auth_users` 是全局用户表，其它模块外键指向它。

## 3. 认证机制
- **Web**：登录成功后设置 HttpOnly Cookie `semestra_session`（opaque 随机串，服务端存 hash 于 `auth_sessions`），`Secure; SameSite=Lax; Domain=<COOKIE_DOMAIN>`（托管版为 `.semestra.jyleo.cc`），有效期 30 天、滑动续期（每天最多续一次写库）。同时设置非 HttpOnly 的 `semestra_csrf` Cookie，前端在写请求中放入 `X-Semestra-CSRF` 头（双提交校验）。
- **Native**：`POST /auth/token` 系列返回 `access_token`（JWT，15 分钟，含 `sub`、`sid`）+ `refresh_token`（opaque，60 天，轮换使用，重放检测：已轮换的旧 token 再次使用则撤销整个会话；轮换后 10 秒内的再次使用视为并发请求的竞争，只返回 401、不撤销）。
- **PAT**：`Authorization: Bearer spat_<random>`，按 hash 查找；只允许访问 capability 路由与 MCP 端点，`read` 作用域只能调用 `effect=read` 的 capability。
- 解析顺序：Bearer（JWT 或 PAT）> Cookie。
- 修改密码、重置密码：撤销该用户所有其它会话。
- 删除账户（M13）时撤销全部会话与 PAT。

## 4. 业务流程
### 4.1 邮箱"继续"流程
1. `auth.email.start(email)` → 无论账号是否存在，统一返回 `{ resend_in_seconds, expires_in_seconds }`，并发送验证码邮件（6 位数字）。
2. `auth.email.verify(email, code)` → 成功：
   - 账号已存在：直接创建会话，返回 `{ status: 'signed_in', user }`。
   - 账号不存在：返回 `{ status: 'needs_profile', registration_token }`（短期 15 分钟，绑定该邮箱）。
3. `auth.register.complete(registration_token, display_name, password?)` → 创建用户、会话。密码可选（用户可以只用邮箱验证码登录）。
- 验证码错误计数，超过 5 次作废；重发间隔 60 秒；同一邮箱每小时最多 10 封、同一 IP 每小时最多 30 封。
- 账号存在与否，响应时间与内容一致。

### 4.2 密码登录
`auth.password.login(email, password)`；失败统一返回 `auth.invalid_credentials`；限流：同一邮箱 15 分钟 10 次，同一 IP 15 分钟 50 次，超过返回 `common.rate_limited`。

### 4.3 Google
- 前端使用 Google Identity Services 获取 ID token，`auth.google.login(id_token)` 校验（`GOOGLE_CLIENT_ID`，校验 `aud`、`iss`、`exp`、`email_verified`）。
- 存在相同 `subject` 的 identity → 登录；否则存在相同已验证邮箱的用户 → 自动关联并登录；否则新建用户（昵称取 Google 名称）。
- `auth.google.link(id_token)`（已登录）：该 Google 账号已被别人关联则 `auth.identity_in_use`。
- `auth.google.unlink()`：总是允许，因为邮箱验证码登录始终可用。

### 4.4 找回密码
`auth.email.start(email, purpose='reset_password')` → `auth.password.reset(email, code, new_password)` → 撤销旧会话和全部个人访问令牌（知道旧密码的人可能留下了令牌）、创建新会话。修改密码同样撤销其他会话和全部令牌，`password_changed` 邮件会说明。

### 4.5 修改邮箱
`auth.email.change_start(new_email, password?)` 发码到新邮箱 → `auth.email.change_confirm(code)`；新邮箱已被占用返回 `auth.email_in_use`。开始前需要重新验证（见 4.7）。确认后撤销其他会话，并给旧地址发 `email_changed` 通知（含新地址，"不是你本人操作就立即联系站点管理员"）。

### 4.7 敏感操作的重新验证
修改邮箱、创建个人访问令牌、删除账户（M13）都走 `require_recent_auth`：会话在 10 分钟内登录过就直接通过；否则有密码的账户要在请求里带当前密码（错误返回 `auth.invalid_credentials`，按用户限流），无密码账户返回 `auth.reauth_required`（`params.password=false`），前端提示重新登录。有密码但没带时返回 `auth.reauth_required`（`params.password=true`），前端显示密码框后重试。前端共用 `modules/auth/components/ReauthFields.tsx`。

### 4.8 清理
`@periodic("auth.cleanup", every=6h)`：删除窗口早于 1 天且未封禁的限流行、过期超过 1 天的验证码、过期或撤销超过 30 天的会话和令牌。

### 4.6 密码规则
最少 8 位，不能与邮箱相同；用 zxcvbn 风格的弱密码黑名单（前 1 万常见密码）拒绝。

## 5. Capabilities 与路由
认证相关的大部分端点涉及 Cookie 设置，放在 `routes.py`，`public=True`，不暴露给 agent/MCP：

| 路由 | 说明 |
|---|---|
| `POST /auth/email/start` | 发送验证码（purpose: continue / reset_password） |
| `POST /auth/email/verify` | 校验验证码 |
| `POST /auth/register/complete` | 完成注册 |
| `POST /auth/password/login` | 密码登录 |
| `POST /auth/password/reset` | 重置密码 |
| `POST /auth/google` | Google 登录 |
| `POST /auth/logout` | 登出当前会话 |
| `POST /auth/token/refresh` | 原生客户端刷新 |
| 以上每个登录端点支持 `?client=native`，返回 token 而不是设置 Cookie |

Capabilities（`expose=("http",)`，账户安全类不给 agent）：
- `account.profile.get` → 用户资料、登录方式（has_password、identities）。允许 agent 读取（`expose` 含 agent，只返回 display_name、email、locale）。
- `account.profile.update(display_name, avatar_url?)`（`avatar_url` 只接受 https 外链或 `null`；传 `null` 会同时删除已上传的头像文件）
- 头像上传是普通路由而非 capability：`POST /account/avatar`（multipart，PNG/JPEG/WebP，≤5 MB）。后端用 Pillow 校验、按 EXIF 旋转、居中裁成正方形并缩放到 256×256，重新编码为 WebP 存入 M00 存储（`users/<id>/avatar/<版本>`），`avatar_url` 指向公开只读的 `GET /account/avatars/<user_id>/<版本>`（版本随机、永久缓存；换头像即换 URL，旧文件随之删除）。头像体积很小，不计入配额。账户删除（M13）需清理 `users/<id>/avatar/`。
- `account.password.change(current_password?, new_password)`（无密码时 current 可空，需最近 10 分钟内登录过，否则 `auth.reauth_required`）
- `account.email.change_start(new_email, password?)`、`account.email.change_confirm`
- `account.google.link`、`account.google.unlink`
- `account.session.list`、`account.session.revoke(session_id)`、`account.session.revoke_others()`
- `account.token.list`、`account.token.create(name, scopes, expires_in_days?, password?)`（明文只在创建时返回一次；需重新验证，见 4.7）、`account.token.revoke(id)`

## 6. 邮件
- `EMAIL_BACKEND`：`resend`（托管版）、`smtp`（自部署）、`console`（开发，打印到日志）。
- 模板：`verification_code`（continue / reset / change_email 三种标题与说明）、`password_changed`、`email_changed`（发往旧地址）、`new_sign_in`（可选，新设备登录通知，默认关闭；"管理设备"链接是 `/?settings=account/security`）。中英两套，语言取用户偏好，未注册用户取请求的 `Accept-Language`。

## 7. 前端
- 路由：`/login`（统一入口）、`/login/reset`、`/settings/account`（资料、登录方式、会话、访问令牌；由 M11 设置框架承载，本模块提供分区组件）。
- 登录页：邮箱输入（`@` 后常见域名自动补全：gmail.com、outlook.com、qq.com、163.com、mail.utoronto.ca 等，可配置列表）→ 验证码（`InputOTP`，6 位，粘贴自动提交）→ 新用户填昵称与可选密码。旁路："使用密码登录"、"使用 Google 登录"。
- 布局：左侧品牌插画区（可选，窄屏隐藏）+ 右侧表单。
- `AuthProvider`：启动时 `account.profile.get`；401 时弹出"会话已过期"对话框（不跳转、保留当前页面状态），重新登录后重试失败的请求；未登录访问受保护路由时跳转 `/login?redirect=...`。
- 登录方式分区：邮箱、密码、Google 三行同一样式，操作按钮都在行右侧。Google 行未关联时在右侧直接渲染 Google Identity Services 的官方按钮（`size: 'medium'`、`shape: 'pill'`，GIS 要求用它自己渲染的按钮，不能换成自绘按钮），拿到 ID token 后调 `account.google.link`；已关联时显示 Google 邮箱和红色"取消关联"，经 `ConfirmDialog` 确认后调 `account.google.unlink`（邮箱验证码登录始终可用，所以不需要"至少保留一种"的额外检查）。
- 访问令牌管理：列表、创建（显示一次明文 + 复制按钮 + "复制 MCP 配置"按钮，生成 Claude Desktop 等客户端可用的 JSON 片段，端点 `<API 源>/mcp`，托管版为 `https://semestra.jyleo.cc/mcp`）、撤销。

## 10. 测试
- 完整流程：continue→verify→register；已有账号 verify 直接登录；密码登录；重置密码后旧会话失效；Google 登录三种分支（mock 验证）；绑定冲突。
- 不可枚举：存在与不存在的邮箱，`email/start` 响应一致。
- 限流：超过阈值返回 `common.rate_limited`，`retry_after_seconds` 正确。
- CSRF：缺头的 Cookie 写请求被拒，Bearer 请求通过。
- refresh token 轮换与重放检测。
- PAT：read 作用域调用 write capability 被拒（`auth.token_scope`）。
- 提供 fixture：`make_user(email=..., password=...)`、`login_as(client, user)`、`bearer_for(user)`。

## 11. 验收
- 新用户 2 分钟内通过邮箱验证码完成注册并进入 onboarding（M02）。
- 会话过期后在当前页面重新登录，未保存的表单内容不丢。
- 所有文案中英双语；邮件中英双语。

## 12. 实现说明（与上文的差异与补充）
以下是 M01 落地时相对本规格的偏差和补充，以代码为准：
- **额外端点**：`GET /auth/config`（登录页读取是否启用 Google、可选的邮箱域名补全等，公开）；`POST /auth/logout` 仅吊销当前会话并清 Cookie；`POST /auth/token/refresh` 接收 `refresh_token`，返回新的 `access_token` + 轮换后的 `refresh_token`；refresh token 被重放时整条会话被吊销。
- **Capability 路径**：`account.*` 的 HTTP 路径为 `/account/me`、`/account/profile`（PATCH）、`/account/password/change`、`/account/email/change-start|change-confirm`、`/account/google/link|unlink`、`/account/sessions[/{session_id}|/revoke-others]`、`/account/tokens[/{id}]`。列表接口（会话、令牌）目前不分页，且仅 HTTP 暴露。
- **PAT 与 MCP**：PAT 只能调用 `expose` 含 `mcp` 的 capability，`read` 作用域只能调用 `effect="read"` 的；目前只有 `account.profile.get` 满足。该规则写在 `Registry.invoke` 中，供 M12 复用。
- **数据表额外字段**：`auth_sessions` 增加 `kind`（web / native）、`previous_refresh_token_hash`（上一个已轮换的 token，重放检测）、`user_agent`、`ip`、`last_used_at`；`auth_email_challenges` 增加 `attempts` / `max_attempts`、`verified_at`、`consumed_at`、`verification_token_hash`（注册令牌）、`request_ip` 等；refresh 轮换用条件 UPDATE 原子完成，只识别上一个 token 的重放（更早的 token 直接 401）；限流计数落在 `auth_rate_limits`（DB 持久化）；`account.email.change_start` 没有客户端 IP，按用户限流（10 次/小时）。见 `0001_*` 迁移。
- **开发期邮件**：`console` 后端在非 prod 环境额外把邮件追加写入 `<data_dir>/dev-outbox.jsonl`，E2E 用它读取验证码。
- **前端 UI 组件**：M01 开发时 shadcn registry 不可达，`src/ui/` 里的组件曾是手写的；之后已用 `shadcn add --all --overwrite` 全部重新生成。页面直接使用官方组件（表单字段 `Field` + `Input`，表单级错误 `FieldError`，对话框 `DialogContent` 自带关闭按钮）。
- **Resend**：托管版使用 `resend` 后端，沿用旧 Semestra 的 Resend 账户、已验证发信域名和 API key（旧 `RESEND_API_KEY` / `AUTH_EMAIL_FROM` / `AUTH_EMAIL_REPLY_TO` 对应 `SEMESTRA_RESEND_API_KEY` / `SEMESTRA_EMAIL_FROM` / `SEMESTRA_EMAIL_REPLY_TO`）。请求形态与旧版一致：Bearer key、以验证挑战 id 作 `Idempotency-Key`、`category` / `purpose` 标签、可选 `reply_to`。区别：邮件正文由本模块按用户语言渲染（中英模板），不使用 Resend 控制台里的托管模板。`backend=resend` 且缺少 key 或发件人时 API 启动即报错。key 只写在服务器 `.env`，不入库、不进仓库。
- **登录检查在 `/_authed` 的 loader 里**：路由器要等所有 `beforeLoad` 结束才开始加载子路由的代码和 loader，所以 `/_authed` 的 `beforeLoad` 只发起请求、不等待，`/account/me` 和外壳代码、外壳数据同时开始；未登录时由 loader 抛出跳转到 `/login?redirect=...`。`/_authed` 下面的路由如果要在 `beforeLoad` 里读数据（会比这个 loader 先跑），先 `await requireSignIn(queryClient, location.href)`（`modules/auth/redirect.ts`），只做跳转的 `beforeLoad` 不需要。
